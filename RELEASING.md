# Release Process

Packages in this monorepo are released through a hardened, tokenless pipeline:
[release-please](https://github.com/googleapis/release-please) (manifest mode) for versioning,
[npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) (OIDC) for authentication,
and a GitHub Environment approval as the final human gate.
**No long-lived npm tokens exist locally or in CI. Never run `npm publish` locally.**

Released packages: `@power-assert/transpiler-core`, `@power-assert/transpiler`,
`@power-assert/runtime`, `@power-assert/node`, `rollup-plugin-power-assert`,
`swc-plugin-power-assert`. (`esbuild-plugin-power-assert` and
`@power-assert/integration-tests` are private and never published.)

## Day-to-day development

- **Conventional Commits drive releases.** All packages are pre-1.0 with
  `bump-minor-pre-major`: `fix:` → patch, `feat:` → minor, and breaking changes
  (`feat!:` / `BREAKING CHANGE:` footer) → minor (not major).
- **Tooling changes must use `chore:` / `ci:`.** A `feat:`/`fix:` commit scoped to a
  package triggers an unintended release PR — this mistake has actually happened.
- To force a specific version, add a `Release-As: x.y.z` footer to a commit
  (an empty commit works):

  ```bash
  git commit --allow-empty -m "chore(runtime): release" -m "Release-As: 0.4.0"
  ```

- When releasable commits land on `main`, release-please creates or updates a
  release PR (`chore: release main`). Cross-package dependency ranges between
  released packages are rewritten automatically (node-workspace plugin), and
  dependents receive a cascading patch bump.
- **CI does not run on release PRs** (a GITHUB_TOKEN limitation). This is
  acceptable because the publish job rebuilds and tests everything immediately
  before publishing.
- **A release PR is not refreshed when base changes leave the release notes
  unchanged.** If a stale release PR must pick up base changes (e.g. lockfile
  or workflow fixes), close it, delete its branch, and re-run the Release
  workflow (or merge any commit to `main`) to have it recreated.

## CHANGELOG policy

- CHANGELOG entries are generated by release-please. Do not edit style or
  wording of generated entries.
- **Factually wrong entries may be corrected by hand on the release PR** — for
  example an API that was added and then consolidated away within the same
  release (see ADR-007 for a real case). Edit both the CHANGELOG file on the
  release PR branch *and* the PR body (GitHub Release notes are taken from the
  body), then merge promptly — a release PR regeneration would discard the
  hand edits.
- Never rewrite merged history to fix a changelog; the `main` ruleset forbids
  it, by design. Note that release-please's `BEGIN_COMMIT_OVERRIDE` mechanism
  does not work with this repository's plain-merge strategy (it requires
  squash merges).

## Releasing

1. **Review and merge the release PR.** Check the proposed versions and compare
   links (a wrong major bump or a `v0.0.0`-based compare link means tag
   matching is broken), and always review the diff of `.github/workflows` and
   lockfiles before approving anything.
   Also check the CHANGELOGs for **duplicate entries**: when a merged PR's
   title is in Conventional Commits form, GitHub's merge commit carries that
   title in its body, and release-please may extract it as an extra entry
   alongside the PR's actual commits (observed with PR #42, where the merge
   commit produced a second `fix:` entry; the trigger conditions are not fully
   understood, so check every release). Remove the duplicate — the entry
   linking the merge commit — by hand-editing the release PR per the
   CHANGELOG policy above.
2. **Approve the `npm` environment deployment**
   (Actions → the waiting Release run → Review deployments → `npm`).
3. The publish job runs `npm ci --ignore-scripts`, `npm run build:dist`,
   `npm run test:dist`, then publishes each released package with
   `npm publish --provenance` via OIDC. release-please has already created the
   `<component>-vX.Y.Z` tags and GitHub Releases.
4. **Verify**: the provenance section appears on each npm package page, and
   `npm audit signatures` reports verified attestations in a consumer project.

## Recovery

- **Publish leg failed after tags/Releases were created**: fix the workflow on
  `main`, then re-run via Actions → Release → Run workflow
  (`workflow_dispatch`). Pass the remaining paths as a JSON array, excluding
  packages that already published successfully, e.g.
  `["packages/runtime", "packages/node"]`. Re-running the failed job would
  reuse the old workflow definition — always use the manual dispatch.
- Tags are currently deletable (tag ruleset and immutable releases are
  deliberately deferred), so deleting a tag and re-releasing is still an
  option during the ramp-up period. Once immutable releases are enabled,
  failed versions become permanent gaps: accept the gap and release the next
  number.
- **Break-glass (OIDC/trusted-publishing outage)**: on npmjs.com create a
  granular access token (7-day expiry, limited to the affected packages),
  publish locally with it, delete the token immediately afterwards, and
  restore the "disallow tokens" publishing access setting.
- **Published by mistake**: `npm unpublish` within 72 hours, `npm deprecate`
  after that.

## Rust (swc-plugin-power-assert)

- `Cargo.toml` carries a `# x-release-please-version` annotation; release-please
  rewrites the version directly (generic updater, `extra-files`).
- `Cargo.lock` is synced by the `sync-release-pr` job on the release PR branch
  (`cargo update -p swc-plugin-power-assert`; note the hyphenated crate name).
  Both are no-ops when swc-plugin-power-assert is not part of the release.

## Configuration map

| Where | What |
|-------|------|
| `.github/workflows/release.yml` | release-please job + release-PR lockfile sync job + publish job (environment `npm`, OIDC, per-package publish loop, `workflow_dispatch` recovery path) |
| `release-please-config.json` / `.release-please-manifest.json` | manifest-mode config: `bump-minor-pre-major`, `include-component-in-tag` (`<component>-vX.Y.Z` tags), node-workspace plugin with `updatePeerDependencies`, `Cargo.toml` extra-files |
| npm package settings (×6) | Trusted Publisher: repo `twada/power-assert-monorepo`, workflow `release.yml` (filename only), environment `npm`, allowed action `npm publish` only. Publishing access: 2FA required, tokens disallowed |
| GitHub repo settings | Environment `npm` (required reviewer, deployment branch `main` only, no admin bypass), branch ruleset `protect main` (PR required, no force-push/deletion, no bypass), read-only default workflow permissions |
